# Changelog

## [1.8.0] - 2026-10-21

Packages: `otlp-ingester` 1.8.0, `runtime-node` 1.7.0, `runtime-next` 1.7.0; `runtime-browser` 1.6.0, `runtime-edge` 1.1.0 and `runtime-cli` 1.2.0 are unchanged. Python services on plain OpenTelemetry (EI-25), what the ingester refuses or drops per repository (EI-27), and one request is one count (EI-26). Any deploy order works: older ingesters ignore the new SDK attributes, and the 1.8.0 migrations (0018–0020) run at boot.

### Features

- Rejections and drops per repository (EI-27, compat feature `ingest_drop_counts`, migration `0018-runtime-ingest-drops`): every request the ingester refuses and every record it does not store is counted per tenant, minute, route and reason in the new `runtime_ingest_drops` table (SummingMergeTree: `requests`, `records`; `kind` is `rejected`, `dropped`, `truncated` or `unforwarded`; `status` is the HTTP status answered). Rejections: `missing_key`, `unknown_key` and `key_unverified` (401; the validator could not answer), `upload_key_not_allowed`, `client_key_not_allowed`, `origin_not_allowed` (403), `rate_limited` (429), `invalid_payload` and `request_aborted` (400), `payload_too_large` (413), `unsupported_media_type` (415), `unknown_route` (404, e.g. a collector endpoint ending in `/v1/traces`), `internal_error` (500), `storage_unavailable` (503). Drops inside accepted requests: `spans_over_limit`, `log_records_over_limit`, `cumulative_histogram`, `memory_point_invalid`, `memory_points_over_limit`, `invalid_event`, `events_over_limit`, `profile_samples_over_limit`; `attributes_truncated` counts attribute values cut; `sink_overflow`, `sink_rejected` and `sink_gave_up` count occurrences the sink webhook gave up on. `records` counts spans, log records, data points or browser events, also for refused requests where the body can tell (a protobuf body is counted from its wire format, never decoded). A key that does not resolve is counted against the null tenant (`org_id = ''`), with `key_hash` = sha256 of the key when it has an Autter prefix, the hash Autter keeps for every key it issued, so the dashboard can show a revoked key that is still sending. Counting never slows or fails ingest: rows are written every 5 s, a failed or stalled write is logged and dropped, never retried, and the buffer is bounded (10,000 rows, 1,000 key hashes per write). See [docs/ARCHITECTURE.md § Rejections and drops](docs/ARCHITECTURE.md#rejections-and-drops) (`otlp-ingester`).
- OTLP partial success: when an accepted export had records dropped (spans past 5,000, log records past 2,000, cumulative `http.server.duration` / `http.server.request.duration` histogram points, invalid or excess memory points), the answer carries `partial_success` with `rejected_spans` / `rejected_log_records` / `rejected_data_points` and an `error_message` that names the limit and the fix, as JSON (`{"partialSuccess":{"rejectedSpans":"3","errorMessage":"…"}}`) and as the protobuf `Export*ServiceResponse`, so OpenTelemetry Collectors log the loss. Fully accepted exports answer as before (`otlp-ingester`).
- How each service's telemetry arrives (compat feature `telemetry_sender_via`, migration `0019-sdk-versions-via`): `runtime_sdk_versions.via` is `collector` (an OpenTelemetry Collector or similar agent, from the User-Agent or an `otelcol` `telemetry.distro.name`), `direct` (an SDK exporter, or a browser with a client key), `relay` (browser events through a server-key relay) or `''`. An Autter SDK behind a collector keeps its own name and is seen as collector-fed; a collector-fed resource with no SDK identity gets a row with an empty SDK name (`otlp-ingester`).
- Resolved and unresolved browser frames per occurrence (compat feature `frame_resolution_counts`, migration `0020-occurrence-frame-resolution`): `runtime_error_occurrences.in_app_frames_resolved` / `in_app_frames_unresolved`, counted after symbolication (in-app frames a source map resolved, and in-app `.js`/`.mjs`/`.cjs` frames it left as parsed), so the share of unresolved frames per release or issue (the EI-14 "over 30%" rule) is read from every occurrence instead of approximated from issue samples (`otlp-ingester`).

- Always-on error spans for Python: `adapters/python/autter_tracing.py`, copied next to `redact.py` (needs `opentelemetry-sdk`; tested with 1.20, 1.27 and 1.41 on Python 3.9 and 1.45 on 3.14). Head sampling drops a trace's exceptions with it, and the Python SDK exports sampled spans only. `RecordUnsampled(sampler)` records what the head sampler drops (`RECORD_ONLY`, keeping the attributes the span started with, which the SDK 1.45 `AlwaysRecordSampler` loses), and `RetainErrorTraces(processor)` sends an unsampled trace, whole, to the exporting processor once one of its spans ends with an `exception` event or ERROR status: the spans that ended before and those that end after, each with the sampled flag and `autter.tail_retained = true`, as `@autter/runtime-node` marks the traces it retains, so the ingester counts no request from them and each error on them once. A trace whose first local span ends healthy is dropped; memory is bounded (256 spans per trace, 5,000 spans and traces, 30 s per trace) and reset in forked workers (gunicorn `--preload`, Celery prefork). `RedactingSpanExporter` scrubs span names, attributes, status messages, exception messages and tracebacks with `redact.py` before export. `init_tracing()` wires all of it from the `OTEL_*` variables; under `opentelemetry-instrument` it keeps the wrapper's provider and warns when that sampler drops errors (`adapters/python`).
- Tested recipes in `examples/python`, with pinned requirements: Django (`runserver`; a `ClientErrorResponses` middleware, because OpenTelemetry's Django middleware records `Http404`, `PermissionDenied`, `BadRequest` and `SuspiciousOperation` as errors; the zero-code `opentelemetry-instrument` variant at full sampling), FastAPI (uvicorn; an `ExceptionGroup` from `asyncio.TaskGroup`), Flask (gunicorn, with and without `--preload`) and Celery (a prefork worker set up in `worker_process_init`, fed through kombu's filesystem transport; a solo worker on the memory broker). Each test starts the app configured by the `OTEL_*` variables alone, at sampling ratio 0 so that only the always-on path exports, against a stub OTLP/HTTP receiver, triggers an unhandled and a handled exception, and checks the `exception` event's type, message and full traceback (the source lines marked `# frame:`), the route, the status, the resource and the `x-autter-key` header. New CI job `python` runs them, and the adapter tests with the SDK installed.
- Ingest tests over what those apps really exported (`packages/otlp-ingester/test-fixtures/python`, OTLP/JSON and the exporter's protobuf, paths replaced): type, message, frames innermost first at the marked lines, in-app frames = the app's files, the `frames-v3` parts; a Django 500 recorded on the request span and on the app's own span is one occurrence and one error, head-sampled or tail-retained; FastAPI's errored `http send` span without an exception is dropped; Celery failures group per task; and the protobuf body, posted as the exporter posts it, reaches the sink with its frames (`otlp-ingester`).
- Docs: [`docs/INTEGRATIONS.md` § Python](docs/INTEGRATIONS.md#python-django-fastapi-flask-celery): install, configuration by environment variables only (`x-autter-key=…` in `OTEL_EXPORTER_OTLP_HEADERS`), where `init_tracing()` goes per framework, how always-on errors work, the zero-code path, unhandled and handled exceptions per framework, troubleshooting; the same pattern for Go, Java, Ruby and .NET (untested here), and pointers from the README, GETTING-STARTED and WITHOUT-NPM.

### Changes

- `request_count` in `runtime_metrics_1m` (and so the sink's `requestCount`, the platform's hourly `total_count`) counts requests and only requests; `error_count` counts failed requests and errors outside any request. Until now every error occurrence outside a span-fed request also counted as a request: a worker's error, a browser error, a promoted edge or logger-only error record, and, for `@autter/runtime-node` apps, every error in a tail-retained trace (so an Express 500 with its exception counted 2 requests and 2 errors, one from the metric feed and one as an event). Now an error recorded in a request makes that request a failed one, once however many errors it records, and adds no request; a 5xx the metric feed already counted adds nothing more from its exception in the same batch, while a request the metric saw succeed adds one error. Errors outside any request (jobs, workers, consumers, browser-only, promoted log records, a `captureException` span exported apart from its request) add `error_count` 1 each and no request. Warnings and info messages add nothing (they were events). Browser `track_event` and timing counters keep their synthetic routes (`event:<name>`, `browser.longtask`, `browser.resource:*`) in `request_count`. `duration_sum_ms / request_count` is now the mean request latency (zero-duration error events no longer dilute it); `error_count / request_count` can exceed 1 for a service whose errors happen outside requests (`otlp-ingester`).

### Fixes

- A value the OTLP normaliser could not read (a timestamp that is not an integer, a list that is not one) threw out of the route handler: an unhandled rejection that stopped the ingester process. It is a 400 now, and any other error in a route handler is a 500 instead of a crash (`otlp-ingester`).
- An OTLP body that is neither `application/json` nor `application/x-protobuf` got a 200 and stored nothing; it gets a 415, as the OTLP spec says (`otlp-ingester`).
- One invalid browser event (a type the ingester doesn't know, a bad timestamp, an oversized field) rejected the whole payload with a 400, and more than 50 events did too; the event is now dropped alone and counted, and the first 50 events are kept. The 202 answer adds `rejected` and the first `issues` (`otlp-ingester`).
- More than 2,000 log records in one request got a 400 for the whole request; the first 2,000 are stored and the rest rejected in `partial_success`. More than 5,000 spans were cut silently; the rest are now answered and counted the same way (`otlp-ingester`).
- Python exception groups (3.11+) parse to the group's own frames, from its `|`-margined block. Before, a group had no frames at all (its issue fell back to the message), and a group raised while handling another exception took that exception's frames. Python standard library frames (`<frozen …>` modules and an installation's `lib/pythonX.Y/` or `PythonXY\Lib\` directory) are no longer in-app, as Go's runtime and JVM/.NET framework frames are not: the five `frames-v3` frames of an `asyncio`, `json` or `socket` error were all standard library frames, so different call sites failing in one library call merged into one issue. Python errors with standard library frames in their stack, and exception groups, get a new `frames-v3` issue once; `message-v1` is unchanged. Nine new Python vectors in `stack-parse-vectors.json`, built from real Python 3.14 tracebacks; the platform's parser shares them (`otlp-ingester`).
- `caught_exceptions.py` runs on Python 3.9, which has no `threading.gettrace()` (`adapters/python`).
- One request is one count in the usage rollups. A framework that opens its own server span under the HTTP instrumentation's (Next.js's `BaseServer.handleRequest`, some NestJS and Fastify setups, gRPC gateways serving in-process) gave each traced request two server spans, and each added a request, its latency and its error, so request counts, latency and error rates of head-sampled traces were doubled. Within each export batch a request is now its outermost server span: walking up parent links present in the batch, the highest server span of the same process (service, environment, release, `service.instance.id`), stopping where a server span's parent is a client or producer span (a call over the wire, a request of its own even when a service calls itself). Nested server spans add no request; the request keeps the best route among its server spans (Next's `http.route` template, `/blog/[slug]`, over the HTTP span's raw path), the outermost span's latency, and fails when any of its server spans does. An error recorded anywhere inside a counted request fails it instead of adding an event: an Express error recorded on a middleware span counted 2 requests and 2 errors, now 1 and 1. A server span whose parent is not in the batch still counts, so a request whose spans an exporter splits across two batches counts once in each. A resource that sends both `http.server.request.duration` and `http.server.duration` (`OTEL_SEMCONV_STABILITY_OPT_IN=http/dup`) is counted from the stable instrument only, as the latency histograms already were (`otlp-ingester`).
- Requests of `@autter/runtime-node` apps are counted once, from the metric feed, under their route. The SDK has always marked its resource `autter.metrics_wired` (its delta `http.server.duration` counts every request), and the ingester was meant to keep such a resource's spans out of the span-fed rollups, but ignored the mark since August (lost in a merge with tail retention), so sampled requests counted twice, all of them at `traceSampleRate: 1`. Honouring it alone would have cost Next.js apps their per-route counts, because their metrics had no route. So the SDK now also sets `autter.metrics_routes` and marks each request span whose metric carries `http.route` with `autter.metric_has_route`, and the ingester counts a request from the metric alone only then (or when runtime-node's tail retention exported it, as before). A request tail-retained by a sender without a metric feed (the Python retention in `adapters/python`) adds no request and counts its failure once. An older SDK (`metrics_wired` only) and a request whose metric has no route (Koa, Fastify or plain `http` without a router instrumentation) keep span-fed counts, which keep their paths (`otlp-ingester`, `runtime-node`).
- Next.js request metrics carry the route template: `/blog/[slug]`, `/api/items/[id]`, `/_not-found`. The HTTP instrumentation takes the route of both the request span and its `http.server.duration` point from the request's RPC metadata, which nothing set under Next (Next names `http.route` on its own span only after the response has closed). The SDK now copies the `next.route` that Next puts on the spans it opens while serving the request ("resolve page components", "render route (app) …", "executing api route (app) …") at span start, in its sampler, so it works whether or not a span is recorded; a route a router instrumentation set is never replaced, and a template with a dynamic segment is never replaced by one without. Checked with Next 15.5 and 16.4, webpack and Turbopack (`runtime-node`).
- The HTTP instrumentation now applies to servers created before `initAutterServer`. It patches `http` when it is required after the SDK starts; Next.js creates its server before `instrumentation.ts` runs, so a Next app got request spans and `http.server.duration` only from the first request that happened to load `http` again (in our test app the first edge-route request), or never, and an ES module app importing its framework first was in the same place. The SDK requires `http` and `https` right after it starts, which patches `Server.prototype.emit` for servers that already exist (`runtime-node`).

## [1.7.0] - 2026-10-21

Packages: `otlp-ingester` 1.7.0, `runtime-cli` 1.2.0. Deploy the ingester first: upload keys and `sourcemaps verify`'s ingester check need it; nothing else changes for older CLIs and SDKs.

### Features

- `autter-runtime sourcemaps setup [dir]` wires source map upload into a project, for people and coding agents: non-interactive, safe to re-run, `--dry-run`, `--json`, `--install`. It detects the build tool (Vite and the frameworks built on it: SvelteKit, Nuxt, Astro, Remix, React Router, Solid, SolidStart, Qwik; Next.js; webpack and Vue CLI; Rollup; Create React App; Angular CLI; Parcel; esbuild), the package manager, the CI (GitHub Actions, Vercel, Netlify, Cloudflare Pages, GitLab CI), the output directory and URL prefix, existing source map settings, the installed `@autter/runtime-browser`/`@autter/runtime-next` and whether `initAutterBrowser` gets a `release`. It adds `@autter/runtime-cli` to `devDependencies`, adds the Vite/Rollup or webpack plugin or wraps the Next.js config in `withAutterSourceMaps` (outermost) when the config has a shape it can edit safely (parsed as JavaScript or TypeScript with acorn and `@sveltejs/acorn-typescript`, new dependency; only the import and the plugin are spliced in), and gives builds without a plugin (CRA, Angular, Parcel, esbuild) a `postbuild` step (appended to `build` for pnpm, Yarn 2+ and Bun) plus hidden maps where the tool supports them (`GENERATE_SOURCEMAP=true`, Angular `"sourceMap": { "scripts": true, "hidden": true }`). Anything it can't do confidently, a missing `release` among them (app code is never edited), becomes a `manual` action with the exact snippet. It never writes a key: `secret.where` gives, per CI, the command that stores `AUTTER_RUNTIME_KEY` reading the value from a prompt or stdin (`gh secret set … --repo <owner/repo>`, `vercel env add … production`, `netlify env:set … "$(cat)"`) or a dashboard note (Cloudflare Pages, GitLab). Exit `0` all applied, `2` manual actions remain, `1` error (`runtime-cli`).
- `autter-runtime sourcemaps verify <dir>` checks a production build before deploy: every JS bundle carries a debug id (comment and snippet, same id), no `.map` is left and no `sourceMappingURL` points at a missing map or inlines one (deploy risks), and with `AUTTER_RUNTIME_KEY` every bundle's map is on the ingester; without a key the upload is reported as unverified. Files copied unchanged from `public/`, Next.js build manifests and polyfills, and service workers are skipped; `--ignore`, `--allow-maps`, `--json`; exit `1` on any failure with the reason per file. Also `verifyDir()` (`runtime-cli`).
- Upload-only keys (`autter_rtu_…`, key scope `upload`, compat feature `sourcemap_upload_keys`): accepted on `/v1/sourcemaps` and `/v1/sourcemaps/check` only; every other authenticated route answers `403 {"error":"upload_key_not_allowed","detail":"autter_rtu_ keys can only upload source maps …"}`. Server keys keep every route; client keys stay refused on the source map routes (now with a message that names upload keys). Static `AUTTER_INGEST_KEYS` entries take `"scope": "upload"`, and an `autter_rtu_…` entry without a scope is an upload key; an entry or validator answer with an unknown scope is now refused instead of becoming a server key. Validator requests carry `x-autter-ingester-version`, so a validator can avoid answering `"upload"` to ingesters before 1.7.0, which treat every scope but `client` as `server` (`otlp-ingester`).
- `/v1/sourcemaps/check` answers entries that name a debug id without a hash: present when any map with that id is stored for the tenant, whatever its release and path (what symbolication would find), so a build can be checked after its maps were deleted. Compat feature `source_map_verify` (`otlp-ingester`).
- The CLI and plugins accept `autter_rtu_…` keys, and their messages recommend an upload-only key for CI (the server key also works); a 401/403 for an upload key says it needs ingester 1.7.0+. New `upload --best-effort` for build scripts: no key or a failed upload is reported and exits `0`, and with `--delete-after-upload` every map under the directory is deleted anyway, so a build never ships maps (`runtime-cli`).
- The `upload-sourcemaps` GitHub Action takes an upload-only key in `key`, and runs `sourcemaps verify` after the upload (`verify`, default `"true"`; leftover maps fail it only with `delete-after-upload: "true"`; skipped with a notice for runtime-cli before 1.2.0; `verify-ignore` for non-bundle JS).

### Fixes

- One thrown error is one occurrence, even when several spans of its trace record it. In a Next.js 15/16 app a route handler error was recorded by `@autter/runtime-node` on the HTTP server span and again by Next's "executing api route" / render span (OpenTelemetry `recordException`), and Next's errored `BaseServer.handleRequest` span added a stackless `HttpServerError`: every error counted two or three times in its issue, its event counters and the incident threshold (Express, Fastify, NestJS and gRPC instrumentations do the same). Within each export batch the ingester now merges `exception` events of the same trace, service, environment and release that sit on different spans, one an ancestor of the other, with the same type (or OTel JS's `error.code` in place of the type, as for Prisma's `P2002`), the same normalised message, in-app frames that are equal or a prefix/suffix of each other, recorded within 5 s. Events on one span or on sibling spans stay separate, so a retry loop recording each attempt keeps every attempt, and each per-attempt child span pairs with its own parent capture. The merged occurrence is the Autter SDK's recording (else the one with runtime-next's `onRequestError` context, else the one nearest the root): it keeps that recording's type, message, severity, time and batch position, so its deterministic occurrence id is unchanged and retries stay idempotent, and takes the rest from the other recordings (attributes, stack, route, method, status, request id, declared `autter.error.*` fields, fingerprint override, breadcrumbs; `autter.merged_recordings` counts them). A status-only `HttpServerError`/`SpanError` is dropped when an unhandled error-severity exception or failed outcome of the same service sits on an ancestor or descendant span in the batch; it is kept when it is the trace's only signal, or the link is not visible. Usage rollups count each thrown error once. Spans of one trace exported in different batches (an exporter timer firing mid-request) are not compared, and the platform does not merge them either (`otlp-ingester`).

## [1.6.1] - 2026-10-21

Packages: `runtime-node` 1.6.1, `runtime-next` 1.6.1, `runtime-cli` 1.1.0, `otlp-ingester` 1.6.1. `runtime-browser` 1.6.0 and `runtime-edge` 1.1.0 are unchanged. Upgrade `runtime-cli` now: 1.0.0's bundler plugins could leave source maps in the deployed output (see Security). CLI 1.1.0 works with ingester 1.6.0, which accepts maps up to 5 MiB; 1.6.1 takes up to 32 MiB.

### Features

- Source maps up to 32 MiB (was 5 MiB), so large vendor chunks are symbolicated too. The CLI and bundler plugins gzip each upload (`Content-Encoding: gzip`, about 3× smaller) and warn that ingester 1.6.0 and older answer 413 above 5 MB (`runtime-cli`). `/v1/sourcemaps` checks the key before reading the body, inflates gzip/deflate and counts its limit (32 MiB + 1 MiB) in inflated bytes; source map inserts run with `input_format_parallel_parsing = 0`, so one large JSON row is not split into 10 MiB parse chunks (no migration: the `map` column is already a ZSTD-compressed `String`). The parse cache decodes `mappings` into one `Int32Array` (about 3 bytes per byte of map JSON, against about 14 for the general-purpose decoder it replaces for lookups) and counts what maps actually take; a map that would need more than half of `SOURCE_MAP_CACHE_MB` is resolved in one pass over its encoded mappings for the whole stack and not kept, so it never flushes the cache (`otlp-ingester`).
- `@autter/runtime-next/client` re-exports `enableTracePropagation`, `disableTracePropagation` and `TracePropagationOptions` from `@autter/runtime-browser/tracing`, as it does breadcrumbs, so a Next.js app can link browser errors to server traces without depending on `@autter/runtime-browser` directly (`runtime-next`).

### Security

- The Vite/Rollup, webpack and Next.js source map plugins no longer leave source maps they turned on in the build output, where they were deployed and exposed the original source. Every map a plugin generated itself (JS and CSS; for Next.js everything under `.next/static`) is now deleted after the upload step whatever its outcome — a rejected upload (413, bad or publishable key), an unreachable ingester, a dry run — with any `sourceMappingURL` comment naming it, and one line says how many were removed and why. Without `AUTTER_RUNTIME_KEY` (or `key`), a plugin turns no maps on and injects no debug ids at all, so the build is unchanged; with `upload: false` or `deleteAfterUpload: false` the generated maps are kept with a warning not to deploy them. Maps you configured yourself are never touched unless you set `deleteAfterUpload: true` (`runtime-cli`).

### Fixes

- Symbolicated browser frames are named after the function they are in, not their call site (scope-based naming, as Sentry's js-source-scopes and PostHog cymbal's `token.scope()` do it). Until now a resolved frame took the name the source map holds at its CALLER's position, so `const run = actions.captured; await run()` reported the `captured` frame as `run`, and handlers a framework calls got the framework's identifier (`func`, `fn`, `listener`). `autter-runtime sourcemaps upload` and the Vite/Rollup, webpack and Next.js plugins now parse each bundle as served (after `inject`, so positions match the stack) with `acorn` (new dependency), record every function (declarations, expressions, arrows, class and object methods, getters, setters) with its generated range and its original name (its own name, else the binding it is assigned to, else its object or class key; mapped through the map's `names`, else `sourcesContent`; minified names that cannot be mapped are marked unknown, never guessed), and upload them in the map as `x_autter_scopes`: `{ version: 1, names, scopes }`, where `scopes` is a `mappings`-style base64 VLQ string (per scope: start column relative to the previous scope's start on the line, end line relative to the start, end column, and a relative name index that continues the map's own `names`; `names` holds only the names the map lacks, `null` for one that could not be mapped). On a TypeScript-sized bundle (21 688 functions, 5 MB map) that is 187 KB, 3.8% of the map. A bundle that does not parse, or a map that only fits the size limit without scopes, is uploaded without them, with a warning (`runtime-cli`). The ingester names a resolved frame after the innermost scope containing it (`null` for an anonymous function or top-level code); the source map cache's byte budget counts the scope table, and `/v1/sourcemaps` stores the field as sent. Maps without scopes, and malformed `x_autter_scopes`, keep the caller-name rule exactly (`otlp-ingester`). See `docs/SOURCE-MAPS.md`.
- Grouping: `frames-v3` tokens change only for frames resolved through a map uploaded with scopes (new uploads from the new CLI), and only where the call-site name differed from the function's own name, so an issue grouped under the old names gets a new `frames-v3` issue once, from the first release uploaded with scopes; issues still keyed by `message-v1` keep matching it. Different handlers in one file no longer merge into one issue under a shared call-site name (`fn@events.js`). The `frames-v3` contract and `fingerprint-v3-vectors.json` are unchanged, so there is no scheme bump.
- One SDK per process, however many copies of `@autter/runtime-node` are loaded. Next.js bundles a separate copy into `instrumentation.ts` and into each route, so code in routes, server components and server actions (`withRuntimeRequest`, `captureServerException`, `runtimeLogger`, `runtimeContext`, `captureRequestError`, …) used a copy `registerAutter` never started: request summaries went to the console instead of the ingester, and errors `withRuntimeRequest` reported were reported again by `onRequestError`. The started SDK (tracker, always-on exporter, redactor, logger configuration and sinks, the current request, the already-reported marks, breadcrumbs, the compatibility check) now lives on `globalThis[Symbol.for("@autter/runtime-node")]`, and every copy reads and writes it, including the ESM and CJS builds loaded in one process. The object has a layout version (`v: 1`) to which fields are only ever added; a copy that finds a layout it does not know keeps its own state. `shutdown()` clears it, and before any copy starts every copy still prints to the console. `serverExternalPackages: ["@autter/runtime-node"]` is no longer needed for correctness (checked with Next 15.5 and 16.4, webpack and Turbopack); it stays recommended because it keeps the SDK out of the route bundles (`runtime-node`, `runtime-next`).

### Changes

- Query strings no longer leave the process with their values. Every exported span, whichever instrumentation made it (HTTP server and client, undici/fetch, Express, Fastify, Next.js's own spans), has `http.target`, `http.url`, `url.full` and `url.original` cut at the `?`, `url.query` reduced to parameter names (`email=[redacted]&page=[redacted]`, added from the URL when the instrumentation did not set it), and the query removed from span names and Next 15's `next.span_name`. Before, only secret-looking values (`?token=`, emails, keys) were masked, and Next's `GET /path?…` span names were stored as sent. New `keepQueryParams: ["page", "sort"]` keeps the values of listed parameters in `url.query`. The policy applies with `redactAttributes: false` too. Autter reads route templates (`http.route`), never query values (`runtime-node`).

## [1.6.0] - 2026-10-21

Packages: `otlp-ingester` 1.6.0, `runtime-node` 1.6.0, `runtime-next` 1.6.0, `runtime-browser` 1.6.0, `runtime-edge` 1.1.0, new `runtime-cli` 1.0.0. Additive: every new field is optional and older ingesters ignore it. Deploy otlp-ingester 1.6.0 first (migrations 0016–0017 run at boot), then SDKs.

### Features

- Server errors keep their stacks: `autterErrorHandler()` (Express/Connect error middleware that calls `next(err)` unchanged), `autterFastifyErrors` (Fastify `onError` hook, as a plugin or `autterFastifyErrors(app)`) and `autterKoa()` (Koa middleware that rethrows) record a thrown error, with its stack, on the request span. Previously the framework's 500 reached the ingester as a stackless `HttpServerError` grouped by route. By default they report status ≥ 500, RuntimeErrors and coded errors (`capture` option). New `captureRequestError(error, attributes?)` for other frameworks: reported once, on the request's HTTP server span even when a child span is active (`runtime-node`).
- Unhandled promise rejections are recorded as errors (`autter.unhandled_rejection: true`, not fatal) without changing whether the process crashes. When Node would crash (default `--unhandled-rejections=throw`, no other listener) the rejection is rethrown on the next tick, so it still exits with code 1 and is recorded as a fatal crash as before; `warn-with-error-code` keeps its warning and exit code; `strict` is left to the crash monitor. Opt out with `captureUnhandledRejections: false` (`initAutterServer`, `initAutterLogging`) (`runtime-node`).
- Next.js `onRequestError` from `@autter/runtime-next/instrumentation`: errors Next catches in server components, server actions, route handlers and middleware are recorded with their stack and Next's context (`next.route_path`, `next.router_kind`, `next.route_type`, `next.render_source`, `next.digest`, method and query-less path; never headers or cookies). Node: on the request span through `registerAutter`'s tracker. Edge: an `edge-light`/`worker` build with no Node imports sends the error to `/v1/logs` with `autterOnRequestError({ edge })` options. Redirects and `notFound()` are skipped (`runtime-next`).
- `captureEdgeException(options, error, attributes?)` reports one exception outside `withAutter`, skipping errors `withAutter` already reported (`runtime-edge`).
- Breadcrumbs (compat feature `breadcrumbs`): the last 30 steps before an error, oldest first, attached to the error and shown on the issue page. Browser: opt-in `@autter/runtime-browser/breadcrumbs` (`enableBreadcrumbs()`, `addBreadcrumb()`) records requests from the fetch/XHR wrappers (method, path without query, status including 4xx, duration), navigations, clicks (the existing action label) and `console.warn`/`console.error` (opt out with `{ console: false }`), scrubbed like the rest of the event, and attaches them to exceptions, unhandled rejections, request failures, error messages and outcomes; kept out of the main bundle so it stays under 5 KB, and the 1.4 `autter.trail` is still sent. Node: `addBreadcrumb()` scoped to the current request (AsyncLocalStorage), `runtimeLogger` entries recorded as `log` breadcrumbs, attached to exception span events as the `autter.breadcrumbs` JSON attribute; the browser relay forwards `breadcrumbs`. Ingester: validates, bounds (30, 500-char messages, 10 data keys, 16 KB) and scrubs them, stores them under `autter.breadcrumbs` in the occurrence's `attributes` JSON (no migration) and forwards them on the sink as the optional `breadcrumbs` field (`runtime-browser`, `runtime-node`, `runtime-next`, `otlp-ingester`).
- Symbolication at ingest and the `frames-v3` issue identity (EI-14/15): every stack is parsed into structured frames, innermost first (V8, Firefox/Safari, Python reversed from its outermost-first traceback, Go, JVM, .NET, Rust, best-effort Ruby/PHP), with dependency, runtime and extension frames marked not in-app. Browser JS frames are resolved through the release's uploaded source maps before grouping (function names from the map's `names`, `ignoreList` honoured, parsed maps cached in a byte-bounded LRU, `SOURCE_MAP_CACHE_MB`); a lookup or map failure never fails ingest. The new `frames-v3` fingerprint hashes service, error type and up to five in-app `function@file` tokens (no line numbers, route, source or release), so a bug stays one issue across deploys, chunk hashes, preview domains, pages and tiers. Sink occurrences gain optional `frames`, `fingerprints` (every candidate: `manual-v1`, `code-v1`, `frames-v3`, `message-v1`, highest precedence first) and `fingerprintRecord`; `fingerprint`/`fingerprintScheme` stay the legacy identity byte-for-byte. `runtime_error_occurrences` gains `frames` and `fingerprints` (migration `0016-occurrence-frames-fingerprints`). Shared vectors: `stack-parse-vectors.json`, `fingerprint-v3-vectors.json` (`otlp-ingester`).
- Readable stack traces with debug ids (EI-13): new `@autter/runtime-cli` package (`autter-runtime sourcemaps inject|upload`) gives every JS bundle with a map a content-addressed debug id (`//# debugId=`, a `globalThis._autterDebugIds` registration snippet, and `debugId` in the `.map`), and uploads maps in parallel, skipping ones the ingester already has. Release defaults to `GITHUB_SHA`, `VERCEL_GIT_COMMIT_SHA`, `CF_PAGES_COMMIT_SHA`, `GIT_SHA`, then `git rev-parse HEAD`. Bundler plugins: `@autter/runtime-cli/vite` (Vite and Rollup), `@autter/runtime-cli/webpack` and `withAutterSourceMaps` from `@autter/runtime-cli/next`; composite action `.github/actions/upload-sourcemaps`. `/v1/sourcemaps` accepts `debugId` (or reads it from the map) and `.mjs`/`.cjs` bundles; new `/v1/sourcemaps/check`; `runtime_source_maps` gains `debug_id` and `content_hash` (migration `0017-source-maps-debug-id`); `lookupSourceMap` finds a map by debug id, then by release + path (`otlp-ingester`). Exceptions carry `debugIds` for the scripts in their stack, read from `globalThis._autterDebugIds` (`runtime-browser`); the browser relay forwards them, and its `autter-runtime` bin hands `sourcemaps` commands to `@autter/runtime-cli` (`runtime-node`). New compat feature `source_map_debug_ids`. See `docs/SOURCE-MAPS.md`.
- Fingerprint override (`fingerprint_override`): `captureException(err, { fingerprint })` takes a string or up to 10 strings (≤200 chars each) and groups every error that carries it into one issue. Browser: a `fingerprint` field on the event, also settable in `beforeSend`, passed through the relay. Node, logger-only mode and edge: the exception event (or promoted log) attribute `autter.fingerprint`, a JSON array of strings. The ingester carries it as `fingerprintOverride` (scrubbed, bounded) and `manualFingerprint()` hashes it into the `manual-v1` candidate, which wins over every automatic scheme; older ingesters ignore the field (`runtime-browser`, `runtime-node`, `runtime-next`, `runtime-edge`, `otlp-ingester`).
- Browser errors link to server traces (EI-11). New opt-in `@autter/runtime-browser/tracing` (`enableTracePropagation({ tracePropagationTargets })`, about 0.6 KB brotlied; the main bundle grows by 45 B of hooks): same-origin `fetch` and XHR requests, and URLs matching `tracePropagationTargets`, carry an unsampled W3C `traceparent`; an existing `traceparent` is never overwritten and the tracker's own endpoint never gets one. `request_failure` events carry their request's `traceId`; an exception or unhandled rejection carries the trace id of the request that finished or failed in the previous 5 s, when that request was traced (`runtime-browser`). The relay forwards a valid `traceId` (`runtime-node`). Unsampled remote parents are head-sampled at the service's own `traceSampleRate` instead of never, so browser-initiated requests keep their usual sampling (`runtime-node`). `/v1/browser` accepts a 32-hex `traceId` per event and stores it as the occurrence's `trace_id` (sink `traceId`); a malformed one is dropped on its own. Browser occurrences no longer count as duplicates in the `/v1/logs` promotion dedupe (`otlp-ingester`). New compat feature `browser_trace_propagation` (ingester 1.6.0).

### Fixes

- Boundary captures (`autterErrorResponse`, `autterFastify`, `withRuntimeRequest`) land on the request's HTTP server span when an instrumentation's child span is active, so the 500 is not also reported as a stackless `HttpServerError`; a throwing `capture` predicate no longer escapes into the response (`runtime-node`).
- `shutdown()` removes the crash monitor it installed (`runtime-node`).
- Errors from another JavaScript realm keep their type, message and stack. Under `next start`, Next runs edge code in a `vm` sandbox and hands edge route-handler errors to the Node `onRequestError`; they failed `instanceof Error` and were recorded as `"Error: …"` with a stack synthesized at the capture site. New internal `isError` (`Error.isError`, else the built-in error tag) is used wherever an error is recorded (`runtime-node`, `runtime-edge`).
- `captureRequestError` on an error that was already reported (by `withRuntimeRequest`, an error hook, …) still adds its attributes to the request span, without a second exception, so Next's `onRequestError` context is kept for route handlers wrapped in `withRuntimeRequest` (`runtime-node`).
- Edge `onRequestError` hands its delivery to the request's `waitUntil` from Next's request context: Next awaits the hook for middleware but not for errors raised while rendering, so an edge function could finish before the record was sent (`runtime-next`).
- Docs: Next.js apps add `serverExternalPackages: ["@autter/runtime-node"]` to `next.config`. Next bundles a separate copy of the SDK into `instrumentation.ts` and into each route, so without it code in routes (`withRuntimeRequest`, `captureServerException`, `runtimeLogger`) used a copy `registerAutter` never started: request summaries went to the console instead of the ingester, and errors were reported twice (`runtime-next`).

Packages: `otlp-ingester` 1.5.0, `runtime-node` 1.5.0, `runtime-next` 1.5.0, `runtime-browser` 1.4.0, new `runtime-edge` 1.0.0. Additive: 1.4.0 code keeps working unchanged (golden-tested).

### Features

- Request summaries: `autterRequests` (Express/Connect), `autterFastify` and `withRuntimeRequest` emit one summary per request with route, status, duration, outcome and a request id. `x-request-id` is honoured or generated, echoed (CORS-exposed) and stamped on spans and records. Summaries are always kept; `ignore` globs skip health/metrics routes (`runtime-node`, `runtime-next`).

- Enrichers (`enrichUserAgent`, `enrichRequestSize`, `enrichEdgeGeo`, `enrichDeployment`), sinks (`otlpSink`, `consoleSink`, `fileSink` writing `.autter/runtime/*.jsonl` in development) and the `@autter/runtime-node/testing` subpath (`runtime-node`).

- `runtime_logs` gains `kind`, `request_id`, `route`, `status_code`, `error_code`, `ai_cost_usd`, `ai_calls` (migration 0012) and feeds the `runtime_request_1m` rollup (migration 0014). `runtime_error_occurrences` gains `error_code`, `error_why`, `error_fix`, `error_link`, `expected`, `request_id`, `fingerprint_scheme` (migration 0013) (`otlp-ingester`).

### Security

- Scrub secrets and PII from exception messages, stack traces and span status messages, not only custom attributes; re-scrub every span at export so third-party instrumentations, HTTP URLs (`?token=`) and `recordException` calls are covered; scrub `LlmCallHandle.setAttributes`, `instrumentLlmClient` attributes and provider errors, and module-level captures made before `initAutterServer` (`runtime-node`).
- New value patterns everywhere: Basic auth, `Authorization:`/`Cookie:`/`Set-Cookie:` header text, connection strings with empty usernames or `@` in the password, `sk-proj-`/`sk-ant-`, Stripe, GitHub fine-grained, GitLab, npm, SendGrid and Google API keys, `password=`/`?token=`/`?api_key=` assignments, Luhn-valid card numbers. New sensitive keys: any `…authorization` header key, `session`/`sessionid`/`sid`, `pwd`, `dsn`, bounded `ssn`. Custom value patterns now apply globally (`runtime-node`, `runtime-browser`, `otlp-ingester`).
- The browser relay scrubs message, stack, name and nested context (`redact` option) (`runtime-node`).
- Browser SDK scrubs messages, stacks and nested context; new `redact: { keys, values } | false` option and `scrubText` export (`runtime-browser`).
- Ingester scrubs occurrence message/stack/route, span names, browser context (deep) and LLM-call attributes before storage and the sink webhook; extra patterns via `AUTTER_REDACT_VALUE_PATTERNS` / `AUTTER_REDACT_KEY_PATTERNS` (`otlp-ingester`).
- Python adapter: new stdlib-only `adapters/python/redact.py` (`redact_text`, `redact_attributes`, `configure`); the caught-exception sampler scrubs tracebacks with it.
- Shared parity vectors in `test-vectors/redaction.json` run against every implementation.
- Export-time scrubbing also covers span link attributes, span event names and resource attributes on traces and metrics (`process.command_args` from NodeSDK's process detector, `OTEL_RESOURCE_ATTRIBUTES`). A batch with a span that could not be scrubbed is reported as a failed export instead of a silent partial success (`runtime-node`).
- The JWT pattern no longer takes seconds on long `eyJ-eyJ-…` runs (5 s per 64 KB in Node, 3.4 s in the ingester, 6 s in the browser); the ingester caps each scrubbed string at 64 KB and cuts context values to their stored size before scrubbing (`runtime-node`, `runtime-browser`, `otlp-ingester`, Python).
- Custom key/value patterns with `g` or `y` flags work on every key and every occurrence (a `/x/g` key pattern used to skip every other matching key); browser value patterns mask every match, not just the first (`runtime-node`, `runtime-browser`).
- Messages, names and stacks are scrubbed before they are cut to size, so a secret straddling the limit is masked whole (browser, relay, Python sampler). A browser context with a throwing getter or revoked Proxy is dropped instead of throwing into the app. The `card` key rule no longer masks keys like `discard` or `scorecard`.

### Version compatibility check

- One source of truth for feature requirements: `packages/otlp-ingester/src/compat-manifest.json`. It lists the minimum ingester, ClickHouse migrations, route and minimum SDK versions for each feature. See `docs/COMPATIBILITY.md`.
- New `GET /v1/compat` (public): ingester version, schema state and level, and per-feature availability. Optional `?features=…&sdk=name@version` returns evaluated issues. Every response carries `x-autter-ingester-version`, exposed to CORS on `/v1/browser`. The ingester records the SDK name and version each service sends with (`runtime_sdk_versions`) and its own version (`runtime_ingester_info`), through migration `0015-runtime-compat` (`otlp-ingester`).

Opt out with `compatCheck: false` or `AUTTER_COMPAT_CHECK=0`. The SDK reports itself as `telemetry.distro.name` and `telemetry.distro.version`, and the browser relay forwards the browser SDK version. Both check browser features against the ingester's version header (`runtime-node`, `runtime-next`).
- New `npx @autter/runtime-node doctor`: a one-shot SDK, ingester and schema report. Exits non-zero on a mismatch (`runtime-node`).
- The browser payload carries the SDK version (`sdk`). Older ingesters ignore it (`runtime-browser`).
- Python adapter: new stdlib-only `adapters/python/compat.py`, with `warn_if_incompatible` and `python3 compat.py doctor`.

### Changes

- Console output is a pretty tree outside production; production keeps JSON lines (`runtime-node`).
- Debug/info logged inside an operation are folded into its summary instead of separate records; `logging.inline: false` restores 1.4.0 behaviour (`runtime-node`).
- `cache_read_tokens`, `cache_creation_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `cached_tokens` and `reasoning_tokens` counts are no longer masked as tokens by redaction (`runtime-node`, `otlp-ingester`).

### Fixes

- Value redaction is linear on adversarial strings. The email, URL-credential, JWT, Slack and Autter-key patterns could take seconds to minutes on long runs such as `"a".repeat(65536)`; they now only start a match at the beginning of a run, query-string stripping is procedural, and strings are capped before scrubbing (`runtime-core`, `runtime-node`, `runtime-edge`, `otlp-ingester`, `runtime-browser`). The patterns predate 1.5.0; 1.5.0 routes more input through them.
- `@autter/runtime-edge` keeps the request summary when its queue is full (a summary evicts the oldest plain record), caps warn/error records at 50 per request, and no longer throws from `rt.error` / `rt.captureException` when attributes have throwing getters or are Proxies.
- `@autter/runtime-edge` queues records with the destination (key, endpoint, service, environment) they were created for, and no longer queues records when no key is configured, so a later request can't export them under its own key.
- `/v1/logs` promotion dedupe lookups are bounded: windows of at most 10 minutes, at most 4 per request, newest records first, only for timestamps within the last 24 hours, and a per-tenant budget (`PROMOTION_LOOKUPS_PER_MINUTE`, default 30) (`otlp-ingester`).
- A throwing getter or Proxy on an error's metadata no longer stops `captureException` from reporting the error (`runtime-browser`).
- The sink keeps a numeric `statusCode` of `0` (`otlp-ingester`).
- An invalid `autter.error.code` or request id on an exception event no longer hides a valid one on its span (`otlp-ingester`).
- `proxy-addr` 2.0.8 in the lockfile (CVE-2026-90711; reached through Express in the ingester and examples).
- Package test scripts build the workspace packages they import first, so each suite runs on a clean checkout.
- `runtime-browser` no longer declares a `./dist/index.cjs` entry that the ESM-only build never produced.
- `runtime-next` builds no longer race on `dist/` cleanup and drop `client.d.ts` / `edge.d.ts`.

### Behavior notes

- Error messages that contained secrets now fingerprint on their scrubbed form, so such issues may regroup once (they previously split per secret value).
